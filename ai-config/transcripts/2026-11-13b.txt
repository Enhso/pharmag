❯ /impeccable:impeccable Build the frontend for this project: a minimal agentic 
research assistant that answers compound questions about a local pharmacology   
corpus.                                                                         
                                                                                
### First step: inspect the existing codebase                                   
Before designing or writing code, read the existing backend, API routes,        
response models, and `Dockerfile`.                                              
- Align strictly with the actual response schema of `POST /ask` (and check      
whether any streaming/trace endpoint exists).                                   
- IMPORTANT: `POST /ask` (`{"question": "..."} -> 200`) is a mandatory          
evaluation contract and must remain a standard JSON 200 endpoint.               
  - If the backend exposes a separate streaming endpoint (or you add a          
non-breaking `POST /ask/stream` SSE endpoint), stream live steps there.         
  - Otherwise, do NOT fake intermediate tool results while `POST /ask` is       
pending: show a calm, honest in-progress indicator while awaiting the response, 
then render the actual returned agent trace (`Plan`, `Retrieve`, `Tools`,       
`Review`) as a clean sequential/inspectable progression alongside the final     
answer.                                                                         
                                                                                
### Core product                                                                
- Single-page app served directly by the existing Python backend on port 8000   
(so `[assignment text removed, p. 2]`  
works self-contained with zero extra servers).                                  
- Required visible elements:                                                    
  1. Agent workflow progression surfacing the actual backend steps: Plan        
(sub-questions), Retrieve (passages/files), Tool use (which local tools the     
agent chose), and Review (critic grounding verdict / any flagged unsupported or 
clinically ambiguous claims). Keep details understated and optionally           
expandable so they stay quiet by default.                                       
  2. Final cited answer (safely rendered Markdown supporting lists,             
comparisons, and inline citations).                                             
  3. Source file references (e.g., `dailymed-warfarin.md`, `GLOSSARY.md`).      
  4. Persistent, non-dismissible disclaimer that the output is for              
research/technical demonstration only and is not medical advice (anchored       
cleanly at the bottom once an answer is displayed).                             
  5. Quiet inline error state with retry if a request fails, preserving the     
user's question.                                                                
                                                                                
### Desired interaction model                                                   
- Extremely minimal interface. The empty state feels almost bare.               
- In the empty state only, clicking anywhere on the page (except on interactive 
elements) focuses a large, centered, auto-resizing `<textarea>` (the text       
cursor is the hero). Do NOT hijack clicks once an answer is rendered so users   
can select text and expand traces normally.                                     
- Pressing `Enter` (ignoring IME composition; `Shift+Enter` for newline) or     
`Cmd/Ctrl+Enter` submits the question.                                          
- Include 3–4 whisper-quiet, clickable sample queries in the empty state        
(reflecting actual corpus drugs/questions) that fade out once the user types or 
submits, so first-time reviewers immediately see what the corpus covers.        
- After submit, the input transitions to a secondary header/reference state and 
the screen reveals the agent's step progression and final cited                 
monograph-style answer.                                                         
- Provide an effortless way to start a new query (`New question` action or      
editing the query / `Esc`) without clutter. No chat history, no sidebars, no    
extra chrome unless it earns its place.                                         
                                                                                
### Aesthetic direction                                                         
Commit to a "blank pharmaceutical / high-end cosmetic" look:                    
- Generous white space, monkish restraint.                                      
- Clean, highly legible neutral sans-serif system stack (Inter / SF Pro /       
system-ui — zero external font dependencies that could fail in an isolated      
container) plus crisp monospace solely for source filenames/tool names if       
helpful.                                                                        
- Near-black text on pure or off-white background.                              
- Extremely limited color: one muted clinical accent at most, used sparingly    
for the active step, citations, or critic warning badges.                       
- Typography does the hierarchy work. No cards with heavy borders, no           
gradients, no decorative lines, no AI-beige defaults.                           
- The overall feeling: serious, clinical, quiet, precise — like high-end        
apothecary packaging or a well-typeset medical information leaflet, never a     
hospital portal or startup landing page.                                        
                                                                                
### Technical constraints                                                       
- Prefer plain, modern HTML + CSS + vanilla JS (zero build step, zero external  
CDN runtime dependencies) mounted cleanly in the existing FastAPI/Python app    
and verified against the `Dockerfile`.                                          
- Responsive on mobile viewports so the centered layout and long comparative    
answers remain intentional.                                                     
- Accessibility basics: semantic landmarks, focus management, keyboard          
navigation, `aria-live` updates for status/answer transitions, high readable    
contrast.                                                                       
                                                                                
Start by shaping the experience (confirming the backend contract, interaction   
states, step progression, and layout) before writing any code. Then implement a 
polished, production-ready version that matches the direction above. Prefer     
quiet excellence over visual noise.

  - POST /ask returns answer, sources, citations, plan, tool_calls, critic,
    disclaimer, timings, usage. It stays as it is.
  - No streaming endpoint exists yet. pipeline.answer(question, engine, emit)
    already emits stage and tool-call events, and DEC-012 already rules that a
    second streaming endpoint feeds the page.
  - The writer emits plain paragraphs, -  bullets and [n] markers only (its
    prompt forbids headings, bold and tables).
  - answer already ends with the cautions, source list and disclaimer as text,
    so the page must build those from the structured fields and cut that tail
    from the prose.

  Shape brief

  - Job: a first-time reviewer opens the page cold, asks one compound question,
    and must see how the agent worked and where every sentence comes from.
  - States: empty → working → answered, plus refusal (out of scope), error with
    retry, and cancelled.
  - Empty: a bare page with one large centred textarea and four whisper-quiet
    sample questions. A click anywhere focuses the textarea. Enter or
    Cmd/Ctrl+Enter submits.
  - Working and answered: one reading column, in this order:
    a. The question as a quiet header, with New question beside it. Esc does the
       same and keeps the old question selected for editing.
    b. Four step rows, each one line and expandable.
    c. The answer, with [n] markers linking to their source.
    d. Cautions, when the critic flagged any.
    e. Sources: file names, with section, lines and quote folded under each.
    f. The disclaimer, pinned to the bottom.
  - Steps: Plan, Retrieve, Write, Review. Retrieval in this backend is tool use,
    so the Retrieve row names the tools the agent chose and the passages they
    returned, rather than showing two rows for one stage.
  - Direction: yours, taken whole from the brief (white ground, near-black
    system sans, monospace for file and tool names only, one muted accent, no
    cards). It is fully pinned, so I skip impeccable's concept roll. Light theme
    only.
  - Not building: tables, chat history, dark theme, or a fallback from the
    stream to /ask.

  How I plan to run it

  - A sonnet builder in a worktree adds POST /ask/stream and its tests.
  - I write the three page files here, since that is the design judgment the
    skill was invoked for.
  - A fresh reviewer agent checks the finished page.
  - Impeccable adds tracked, public files: PRODUCT.md, a surface brief under
    .impeccable/, and DESIGN.md at the end.
  - The skill is copied into ai-config/ with its manifest row.

  fixture.

  **Wire format.** Every frame is `event: <name>\ndata: <one line of JSON>\n\n`.
  The response is 200 with `Content-Type: text/event-stream; charset=utf-8`,
  `Cache-Control: no-cache` and `X-Accel-Buffering: no`.
  ```
  event: trace
  data: {"stage":"plan","kind":"planned","data":{"in_scope":true,"reason":"A
  label question.","sub_questions":[{"text":"What are warfarin's
  contraindications?","drugs":["warfarin"]}]},"elapsed":1.84}

  event: answer
  data: {<full AskResponse, the same JSON /ask returns>}

  event: error
  data: {"error":"pipeline","stage":"review","detail":"review: <scrubbed>"}

  event: error
  data: {"error":"internal","detail":"ValueError: <scrubbed>"}
  ```
  - `trace` frames come one per pipeline event, in emission order.
  - A successful run ends with exactly one `answer` frame.
  - A failed run ends with exactly one `error` frame.
  - 503 bodies (`configuration`, `index`) and 422 come before any stream, with
  the same JSON as `/ask`.

  **New trace events** (all emitted through `req.event`; `AskResponse` is
  unchanged):
  - `plan`/`planned` carries `in_scope`, `reason` and `sub_questions` as
  `[{"text", "drugs"}]`. It fires inside the plan stage, before its `finished`
  event, and also for an out-of-scope plan.
  - `write`/`drafted` and `retry`/`drafted` carry `claims=<n>`, and fire inside
  their stage block before `finished`.
  - `review`/`reviewed` carries `supported`, `ambiguous`, `unsupported` and
  `unmarked`. It fires at the end of `_check`, after the review stage has
  finished, so `reviewed` comes after `review`/`finished`. `_check` runs again
  in the retry round, so a retried run emits two `reviewed` events.
